# 编写 Skill

## 流程

1. **收集需求** - 向用户询问：
   - 这个 skill 覆盖什么任务/领域？
   - 应该处理哪些具体用例？
   - 需要可执行脚本还是只需指令？
   - 有没有要包含的参考材料？

2. **起草 skill** - 创建：
   - 包含简洁指令的 SKILL.md
   - 如果内容超过 500 行，添加额外参考文件
   - 如果需要确定性操作，添加工具脚本

3. **与用户审查** - 展示草稿并询问：
   - 这覆盖了你的用例吗？
   - 有没有遗漏或不清楚的？
   - 是否有些部分应该更详细/更简略？

## Skill 结构

```
skill-name/
├── SKILL.md           # 主要指令（必需）
├── REFERENCE.md       # 详细文档（如需）
├── EXAMPLES.md        # 使用示例（如需）
└── scripts/           # 工具脚本（如需）
    └── helper.js
```

## SKILL.md 模板

```md
---
name: skill-name
description: 能力的简要描述。Use when [特定触发条件]。
---

# Skill 名称

## 快速开始

[最小可行示例]

## 工作流

[带检查清单的分步过程，用于复杂任务]

## 高级功能

[链接到单独文件：见 [REFERENCE.md](REFERENCE.md)]
```

## 描述要求

描述是你的 agent 决定加载哪个 skill 时**唯一能看到的东西**。它出现在系统提示中，与所有其他已安装的 skill 并列。你的 agent 读取这些描述并根据用户请求选择相关 skill。

**目标**：给 agent 刚好够的信息来知道：

1. 这个 skill 提供什么能力
2. 何时/为何触发它（特定关键词、上下文、文件类型）

**格式**：

- 最多 1024 字符
- 用第三人称写
- 第一句：它做什么
- 第二句："Use when [特定触发条件]"

**好的示例**：

```
从 PDF 文件中提取文本和表格，填充表单，合并文档。当处理 PDF 文件或用户提到 PDF、表单或文档提取时使用。
```

**坏的示例**：

```
帮助处理文档。
```

坏的示例让你的 agent 无法将此与其他文档 skill 区分。

## 何时添加脚本

以下情况添加工具脚本：

- 操作是确定性的（验证、格式化）
- 相同代码会被重复生成
- 错误需要显式处理

脚本比生成的代码更省 token 且更可靠。

## 何时拆分文件

以下情况拆分为单独文件：

- SKILL.md 超过 100 行
- 内容有不同领域（金融 vs 销售的 schema）
- 高级功能很少用到

## 审查检查清单

起草后验证：

- [ ] 描述包含触发条件（"Use when..."）
- [ ] SKILL.md 在 100 行以下
- [ ] 没有时间敏感信息
- [ ] 术语一致
- [ ] 包含具体示例
- [ ] 引用只深一层
