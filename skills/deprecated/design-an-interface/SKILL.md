# 设计接口

基于《A Philosophy of Software Design》中的"Design It Twice"原则：你的第一个想法不太可能是最好的。生成多个截然不同的设计，然后比较。

## 工作流

### 1. 收集需求

设计之前，理解：

- [ ] 这个模块解决什么问题？
- [ ] 调用者是谁？（其他模块、外部用户、测试）
- [ ] 关键操作是什么？
- [ ] 有什么约束？（性能、兼容性、既有模式）
- [ ] 什么应该隐藏在内部 vs 暴露出来？

问："这个模块需要做什么？谁会使用它？"

### 2. 生成设计（并行子 agent）

使用 Task 工具同时启动 3+ 个子 agent。每个必须产出**截然不同**的方案。

```
每个子 agent 的提示模板：

为以下内容设计接口：[模块描述]

需求：[收集的需求]

此设计的约束：[给每个 agent 分配不同约束]
- Agent 1："最小化方法数——目标最多 1-3 个方法"
- Agent 2："最大化灵活性——支持多种用例"
- Agent 3："为最常见情况优化"
- Agent 4："从[特定范式/库]获取灵感"

输出格式：
1. 接口签名（类型/方法）
2. 使用示例（调用者如何使用）
3. 此设计在内部隐藏了什么
4. 此方案的取舍
```

### 3. 展示设计

展示每个设计：

1. **接口签名** - 类型、方法、参数
2. **使用示例** - 调用者实际如何使用
3. **隐藏了什么** - 保持在内部的复杂性

依次展示设计，让用户在比较前消化每个方案。

### 4. 比较设计

展示所有设计后，在这些维度上比较：

- **接口简洁性**：更少方法、更简单参数
- **通用 vs 专用**：灵活度 vs 聚焦度
- **实现效率**：形态是否允许高效的内部实现？
- **深度**：小接口隐藏大量复杂性（好）vs 大接口实现很薄（坏）
- **正确使用的容易度** vs **误用的容易度**

用散文讨论取舍，不用表格。突出设计分歧最大的地方。

### 5. 综合

最佳设计通常结合多个方案的洞见。问：

- "哪个设计最适合你的主要用例？"
- "其他设计中有值得吸收的元素吗？"

## 评估标准

来自《A Philosophy of Software Design》：

**接口简洁性**：更少方法、更简单参数 = 更容易学习和正确使用。

**通用性**：无需修改即可处理未来用例。但警惕过度泛化。

**实现效率**：接口形态是否允许高效实现？还是迫使内部实现别扭？

**深度**：小接口隐藏大量复杂性 = 深模块（好）。大接口实现很薄 = 浅模块（避免）。

## 反模式

- 不要让子 agent 产出相似设计——强制截然不同
- 不要跳过比较——价值在于对比
- 不要实现——这纯粹关于接口形态
- 不要基于实现工作量来评估
