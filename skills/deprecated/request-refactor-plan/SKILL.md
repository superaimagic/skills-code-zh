---

当用户想要创建重构请求时触发此 skill。你应该经过以下步骤。如果你认为某些步骤不必要，可以跳过。

1. 向用户询问他们想要解决的问题的详细描述，以及任何潜在的解决方案想法。

2. 探索仓库以验证他们的断言并理解代码库的当前状态。

3. 询问他们是否考虑过其他选项，并向他们展示其他选项。

4. 就实现方案面试用户。要极其详细和彻底。

5. 敲定实现的确切范围。确定你计划改变什么和不改变什么。

6. 查看代码库以检查该区域的测试覆盖。如果测试覆盖不足，问用户他们的测试计划是什么。

7. 将实现分解为微小 commit 的计划。记住 Martin Fowler 的建议："让每个重构步骤尽可能小，这样你总能看到程序在运行。"

8. 用重构计划创建 GitHub issue。使用以下模板作为 issue 描述：

<refactor-plan-template>

## 问题陈述

开发者面临的问题，从开发者的视角。

## 解决方案

问题的解决方案，从开发者的视角。

## Commit

一个冗长、详细的实现计划。用平实英语写计划，将实现分解为尽可能小的 commit。每个 commit 应让代码库保持可工作状态。

## 决策文档

做出的实现决策列表。可以包括：

- 将要构建/修改的模块
- 这些模块将要修改的接口
- 来自开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 特定交互

不要包含具体文件路径或代码片段。它们可能很快过时。

## 测试决策

做出的测试决策列表。包括：

- 什么构成好测试的描述（只测试外部行为，不测试实现细节）
- 哪些模块将被测试
- 测试的先例（即代码库中类似类型的测试）

## 不在范围内

此重构不在范围内的事项描述。

## 补充说明（可选）

关于重构的任何补充说明。

</refactor-plan-template>
