# 测试驱动开发

## 哲学

**核心原则**：测试应该通过公共接口验证行为，而不是实现细节。代码可以完全改变；测试不应该。

**好的测试**是集成式的：它们通过公共 API 行使真实的代码路径。它们描述系统*做什么*，而不是*怎么做*。好的测试读起来像规格说明——"用户可以用有效购物车结账"准确告诉你有什么能力。这些测试在重构后依然存活，因为它们不关心内部结构。

**坏的测试**与实现耦合。它们 mock 内部协作者、测试私有方法、或通过外部方式验证（比如直接查询数据库而不是使用接口）。警告信号：你重构时测试崩了，但行为没变。如果你重命名一个内部函数测试就失败了，那些测试测的是实现，不是行为。

见 [tests.md](tests.md) 了解示例，[mocking.md](mocking.md) 了解 mock 指导。

## 反模式：水平切片

**不要先写所有测试，然后写所有实现。** 这是"水平切片"——把 RED 当成"写所有测试"，GREEN 当成"写所有代码"。

这产生**垃圾测试**：

- 批量写的测试测的是*想象的*行为，不是*真实的*行为
- 你最终测的是东西的*形状*（数据结构、函数签名）而不是面向用户的行为
- 测试对真实变更变得不敏感——行为坏了它通过，行为正常它失败
- 你超出了你的视野，在理解实现之前就承诺了测试结构

**正确方法**：通过示踪弹进行垂直切片。一个测试 → 一个实现 → 重复。每个测试响应你从上一个循环中学到的。因为你刚写了代码，你确切知道什么行为重要以及如何验证它。

```
错误（水平）：
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

正确（垂直）：
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
  ...
```

## 工作流

### 1. 规划

探索代码库时，使用项目的领域词汇表，使测试名称和接口词汇与项目语言匹配，并尊重你正在触及区域的 ADR。

写任何代码之前：

- [ ] 与用户确认需要什么接口变更
- [ ] 与用户确认要测试哪些行为（优先级排序）
- [ ] 识别[深模块](deep-modules.md)的机会（小接口，深实现）
- [ ] 为[可测试性](interface-design.md)设计接口
- [ ] 列出要测试的行为（不是实现步骤）
- [ ] 获得用户对计划的批准

问："公共接口应该长什么样？哪些行为最重要需要测试？"

**你不可能测试一切。** 与用户确认哪些行为最重要。把测试精力集中在关键路径和复杂逻辑上，不是每个可能的边缘情况。

### 2. 示踪弹

写一个测试，确认系统的一件事：

```
RED:   为第一个行为写测试 → 测试失败
GREEN: 写最小代码让它通过 → 测试通过
```

这是你的示踪弹——端到端验证路径可行。

### 3. 增量循环

对每个剩余行为：

```
RED:   写下一个测试 → 失败
GREEN: 最小代码让它通过 → 通过
```

规则：

- 一次一个测试
- 只写够通过当前测试的代码
- 不要预先为未来的测试做准备
- 保持测试聚焦于可观察行为

### 4. 重构

所有测试通过后，寻找[重构候选](refactoring.md)：

- [ ] 提取重复
- [ ] 深化模块（把复杂度移到简单接口后面）
- [ ] 在自然的地方应用 SOLID 原则
- [ ] 考虑新代码揭示了关于现有代码的什么问题
- [ ] 每次重构步骤后运行测试

**永远不要在 RED 状态下重构。** 先回到 GREEN。

## 每个周期的检查清单

```
[ ] 测试描述行为，不是实现
[ ] 测试只使用公共接口
[ ] 测试在内部重构后仍能存活
[ ] 代码对这个测试来说是最小的
[ ] 没有添加推测性功能
```
