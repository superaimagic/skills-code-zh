# 语言

这个 skill 每个建议的共享词汇。准确使用这些术语——不要用"component"、"service"、"API"或"boundary"替代。一致的语言是重点。

## 术语

**Module（模块）**
任何有接口和实现的东西。刻意忽略规模——同样适用于函数、类、包或跨层切片。
_避免使用_：unit、component、service。

**Interface（接口）**
调用者正确使用模块必须知道的一切。包括类型签名，但也包括不变量、顺序约束、错误模式、所需配置和性能特征。
_避免使用_：API、signature（太窄——那些只指类型级表面）。

**Implementation（实现）**
模块内部的东西——它的代码体。与 **Adapter** 不同：一个东西可以是小 adapter 大实现（Postgres 仓库），也可以是大 adapter 小实现（内存 fake）。当话题是 seam 时用"adapter"；否则用"implementation"。

**Depth（深度）**
接口处的杠杆——调用者（或测试）每单位需要学习的接口能行使的行为量。当大量行为位于小接口后面时，模块是**深的**。当接口几乎和实现一样复杂时，模块是**浅的**。

**Seam（接缝）** _（来自 Michael Feathers）_
一个你可以在不原地编辑的情况下改变行为的地方。模块接口所在的*位置*。选择 seam 放在哪里本身就是一个设计决策，与后面放什么不同。
_避免使用_：boundary（与 DDD 的限界上下文过载）。

**Adapter（适配器）**
在 seam 处满足接口的具体东西。描述*角色*（它填充什么位置），不是内容（里面是什么）。

**Leverage（杠杆）**
调用者从深度中获得的东西。每单位需要学习的接口获得更多能力。一个实现在 N 个调用点和 M 个测试中回报。

**Locality（局部性）**
维护者从深度中获得的东西。变更、bug、知识和验证集中在一个地方，而不是分散在调用者中。修一次，到处修好。

## 原则

- **深度是接口的属性，不是实现的属性。** 深模块内部可以由小的、可 mock 的、可替换的部分组成——它们只是不属于接口。模块可以有**内部 seam**（对其实现私有、由其自己的测试使用）以及接口处的**外部 seam**。
- **删除测试。** 想象删除模块。如果复杂度消失了，模块没有隐藏任何东西（它是透传的）。如果复杂度重新出现在 N 个调用者中，模块在赚它的价值。
- **接口就是测试面。** 调用者和测试穿越同一个 seam。如果你想测试*越过*接口，模块可能形状不对。
- **一个 adapter 意味着假设的 seam。两个 adapter 意味着真正的 seam。** 除非有东西真的跨 seam 变化，否则不要引入 seam。

## 关系

- 一个 **Module** 恰好有一个 **Interface**（它呈现给调用者和测试的表面）。
- **Depth** 是 **Module** 的属性，相对于其 **Interface** 衡量。
- **Seam** 是 **Module** 的 **Interface** 所在的位置。
- **Adapter** 坐落在 **Seam** 处并满足 **Interface**。
- **Depth** 为调用者产生 **Leverage**，为维护者产生 **Locality**。

## 被拒绝的表述

- **Depth 作为实现行数与接口行数的比率**（Ousterhout）：奖励填充实现。我们改用深度即杠杆。
- **"Interface" 作为 TypeScript `interface` 关键字或类的公共方法**：太窄——这里的接口包括调用者必须知道的每一个事实。
- **"Boundary"**：与 DDD 的限界上下文过载。说 **seam** 或 **interface**。
