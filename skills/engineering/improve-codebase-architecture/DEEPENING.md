# 深化

如何安全地深化一组浅模块，考虑其依赖。使用 [LANGUAGE.md](LANGUAGE.md) 中的词汇——**module**、**interface**、**seam**、**adapter**。

## 依赖类别

评估深化候选时，对其依赖进行分类。类别决定了深化模块如何跨 seam 测试。

### 1. 进程内

纯计算、内存状态、无 I/O。总是可以深化——合并模块，直接通过新接口测试。不需要 adapter。

### 2. 本地可替代

有本地测试替代品的依赖（PGLite 替代 Postgres、内存文件系统）。如果替代品存在则可深化。深化模块在测试套件中用替代品运行。Seam 是内部的；模块外部接口没有 port。

### 3. 远程但自有（Port & Adapter）

跨网络边界的自有服务（微服务、内部 API）。在 seam 处定义 **port**（接口）。深模块拥有逻辑；传输作为 **adapter** 注入。测试使用内存 adapter。生产使用 HTTP/gRPC/队列 adapter。

建议形式：*"在 seam 处定义 port，为生产实现 HTTP adapter，为测试实现内存 adapter，这样逻辑就集中在一个深模块中，即使它跨网络部署。"*

### 4. 真正外部（Mock）

你无法控制的第三方服务（Stripe、Twilio 等）。深化模块将外部依赖作为注入 port 接受；测试提供 mock adapter。

## Seam 纪律

- **一个 adapter 意味着假设的 seam。两个 adapter 意味着真正的 seam。** 除非至少有两个 adapter 的理由（通常是生产 + 测试），否则不要引入 port。单 adapter 的 seam 只是间接层。
- **内部 seam vs 外部 seam。** 深模块可以有内部 seam（对其实现私有、由其自己的测试使用）以及接口处的外部 seam。不要仅仅因为测试使用内部 seam 就通过接口暴露它们。

## 测试策略：替换，不要叠加

- 一旦深化模块接口的测试存在，浅模块上的旧单元测试就变成废物——删除它们。
- 在深化模块的接口处写新测试。**接口就是测试面**。
- 测试通过接口断言可观察的结果，不是内部状态。
- 测试应能在内部重构后存活——它们描述行为，不是实现。如果测试在实现变化时也必须改变，说明它测过了接口。
