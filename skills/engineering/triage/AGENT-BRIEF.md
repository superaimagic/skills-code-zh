# 编写 Agent 简报

Agent 简报是在 issue 移到 `ready-for-agent` 时发布在 GitHub issue 上的结构化评论。它是 AFK agent 将要工作的权威规格。原始 issue 正文和讨论是上下文——agent 简报才是契约。

## 原则

### 持久性优于精确性

Issue 可能在 `ready-for-agent` 停留数天或数周。代码库在此期间会改变。写简报时要让它即使在文件被重命名、移动或重构后仍然有用。

- **要**描述接口、类型和行为的契约
- **要**命名 agent 应该查找或修改的特定类型、函数签名或配置形状
- **不要**引用文件路径——它们会变陈旧
- **不要**引用行号
- **不要**假设当前的实现结构会保持不变

### 行为性，不是过程性

描述系统**应该做什么**，不是**怎么**实现它。Agent 会全新探索代码库，并做出自己的实现决策。

- **好：** "`SkillConfig` 类型应该接受一个 `CronExpression` 类型的可选 `schedule` 字段"
- **坏：** "打开 src/types/skill.ts 并在第 42 行添加一个 schedule 字段"
- **好：** "当用户不带参数运行 `/triage` 时，他们应该看到需要关注的 issue 摘要"
- **坏：** "在 main handler 函数中添加一个 switch 语句"

### 完整的验收标准

Agent 需要知道什么时候做完了。每个 agent 简报必须有具体、可测试的验收标准。每个标准应该独立可验证。

- **好：** "运行 `gh issue list --label needs-triage` 返回已通过初步分类的 issue"
- **坏：** "分流应该正确工作"

### 明确的范围边界

说明什么超出范围。这防止 agent 过度实现或对相邻功能做假设。

## 模板

```markdown
## Agent 简报

**类别：** bug / enhancement
**摘要：** 需要做什么的一行描述

**当前行为：**
描述现在发生什么。Bug 的话这是被破坏的行为。
功能请求的话这是功能所基于的现状。

**期望行为：**
描述 agent 工作完成后应该发生什么。
对边缘情况和错误条件要具体。

**关键接口：**
- `TypeName` — 需要改变什么以及为什么
- `functionName()` 返回类型 — 当前返回什么 vs 应该返回什么
- 配置形状 — 需要的任何新配置选项

**验收标准：**
- [ ] 具体、可测试的标准 1
- [ ] 具体、可测试的标准 2
- [ ] 具体、可测试的标准 3

**超出范围：**
- 不应在此 issue 中改变或处理的事情
- 可能看起来相关但独立存在的相邻功能
```

## 示例

### 好的 agent 简报（bug）

```markdown
## Agent 简报

**类别：** bug
**摘要：** Skill 描述截断在词中间，产生损坏的输出

**当前行为：**
当 skill 描述超过 1024 字符时，截断在精确的 1024 字符处，不管词边界。这产生以词中间结尾的描述（例如"Use when the user wants to confi"）。

**期望行为：**
截断应该在 1024 字符之前的最后一个词边界处断开
并追加"..."表示截断。

**关键接口：**
- `SkillMetadata` 类型的 `description` 字段——不需要类型变更，
  但填充它的验证/处理逻辑需要尊重词边界
- 任何读取 SKILL.md frontmatter 并提取描述的函数

**验收标准：**
- [ ] 1024 字符以下描述不变
- [ ] 超过 1024 字符的描述在 1024 字符之前的最后一个词边界处截断
- [ ] 截断的描述以"..."结尾
- [ ] 包含"..."的总长度不超过 1024 字符

**超出范围：**
- 改变 1024 字符限制本身
- 多行描述支持
```

### 好的 agent 简报（enhancement）

```markdown
## Agent 简报

**类别：** enhancement
**摘要：** 添加 `.out-of-scope/` 目录支持以追踪被拒绝的功能请求

**当前行为：**
功能请求被拒绝时，issue 以 `wontfix` 标签和一条评论关闭。没有关于决策或理由的持续记录。
未来的类似请求需要维护者回忆或搜索先前的讨论。

**期望行为：**
被拒绝的功能请求应该记录在 `.out-of-scope/<concept>.md`
文件中，捕获决策、理由和所有请求此功能的 issue 的链接。分流新 issue 时，应该
检查这些文件是否有匹配。

**关键接口：**
- `.out-of-scope/` 中的 Markdown 文件格式——每个文件应该有
  `# Concept Name` 标题、一行 `**Decision:**`、一行 `**Reason:**`，
  和一个带 issue 链接的 `**Prior requests:**` 列表
- 分流工作流应该早期读取所有 `.out-of-scope/*.md` 文件
  并通过概念相似度匹配传入的 issue

**验收标准：**
- [ ] 将功能关闭为 wontfix 时创建/更新 `.out-of-scope/` 中的文件
- [ ] 文件包含决策、理由和指向已关闭 issue 的链接
- [ ] 如果已存在匹配的 `.out-of-scope/` 文件，新 issue 被
      追加到其"Prior requests"列表，而不是创建重复文件
- [ ] 分流期间，检查现有 `.out-of-scope/` 文件并在新 issue 匹配先前拒绝时展示

**超出范围：**
- 自动匹配（人工确认匹配）
- 重新打开先前拒绝的功能
- Bug 报告（只有功能拒绝进入 `.out-of-scope/`）
```

### 坏的 agent 简报

```markdown
## Agent 简报

**摘要：** 修复分流 bug

**做什么：**
分流的那个东西坏了。看主文件并修复它。
大约第 150 行的函数有问题。

**要改变的文件：**
- src/triage/handler.ts (第 150 行)
- src/types.ts (第 42 行)
```

这是坏的，因为：
- 没有类别
- 描述模糊（"分流那个东西坏了"）
- 引用会变得陈旧的文件路径和行号
- 没有验收标准
- 没有范围边界
- 没有描述当前 vs 期望行为
